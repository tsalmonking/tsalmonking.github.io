Your detector is 99% accurate under idealised conditions

Detection accuracy and adversarial robustness are measuring different things, and only one of them appears in most papers.

Pick a recent paper on detecting AI-generated images. It will almost certainly report accuracy above 95%, often above 99%, across several generators. Pick another one. Same. The field looks solved from the abstract.

Then someone runs a gradient through the detector and the number collapses.

This is not a surprising result — it has been the expected outcome for any undefended classifier since roughly 2013. What is surprising is how rarely the check is performed at all. The gap is not a disagreement about findings. It is that two different questions are being asked, and only the easier one is being answered.

Two different questions

The first question is can this model separate real from generated images drawn from a fixed distribution? That is what a test-set accuracy measures. It is a real question and a hard one, especially across generators the model never saw during training.

The second question is can this model separate real from generated images when someone is actively trying to make it fail? No amount of the first answers the second. A model can sit at 99.4% on held-out data and be moved to whatever label you like with a perturbation you cannot see.

Papers that report only the first are not wrong. They are answering a question that the deployment setting does not ask. Detection is a security problem: the images you most want to catch are the ones produced by someone who knows a detector exists.

Why the check gets skipped

Two reasons, and I think the second matters more.

The first is awareness. Plenty of work on generative forensics comes from a multimedia or computer vision background rather than a security one, where the adversarial framing is not the default lens.

The second is cost. Running a proper robustness evaluation is genuinely a lot of work. You need attack implementations, per-model hyperparameters, a compute budget, and enough familiarity with the failure modes to know when your attack is under-optimised rather than the model being robust. A weak attack produces a flattering number, and a flattering number is indistinguishable from a real one unless someone else attacks the model harder later.

This is the failure mode worth naming: an inadequate evaluation does not look inconclusive. It looks like a good result.

So the rational move for an author with a deadline is to skip it, and the resulting literature reports one number that everyone reads as if it were the other.

What a robustness claim has to specify

If you are reporting robustness, the number is meaningless without the conditions attached. At minimum:

  • Threat model. White-box, black-box, or transfer? Does the attacker know the architecture, the weights, the preprocessing?
  • Perturbation budget. Which norm, and what ε. An unbounded attack that visibly wrecks the image proves nothing about a realistic adversary.
  • Attack strength. Number of steps, restarts, step size. An attack that has not converged is not evidence of robustness.
  • The full curve, not one point. Robust accuracy at a single ε hides where the model actually breaks.

A sentence of the form robust accuracy 71% with none of this attached carries no information at all.

The cheaper path: fixed adversarial datasets

The cost problem has a partial answer. If the barrier is that running attacks is expensive and easy to get wrong, then the attacks can be run once, carefully, and released as data.

This is the idea behind RAID: generate adversarial examples with an ensemble attack against a set of detectors, so that they transfer to models that were never part of the ensemble, and ship the result as a fixed dataset. Evaluation then costs a forward pass.

from datasets import load_dataset

raid = load_dataset("pralab/RAID", split="test")
correct = sum(detector(x["image"]) == x["label"] for x in raid)
print(f"robust accuracy: {correct / len(raid):.1%}")

The trade-off is explicit and worth stating plainly. A fixed dataset is a lower bound on attackability, not a certificate. An adaptive attacker who targets your specific model will do better than transferred examples do — that is what adaptive means. What the dataset buys is that the check becomes cheap enough that there is no excuse for omitting it, and that everyone's numbers become comparable because they came from the same examples.

A benchmark's job is not to be the hardest possible attack. It is to make the easy attack impossible to ignore.

It also has a shelf life. Detectors will be tuned against any fixed set of examples, deliberately or not, and once that happens the benchmark measures memorisation instead of robustness. That is fine — it just means these datasets need to be treated as versioned artifacts that get regenerated, not as permanent fixtures.1

What I would like to see become normal

Not much, honestly. A single additional table. Report clean accuracy, report robust accuracy under a stated threat model and budget, and say which attack produced it. If robustness is bad, report that it is bad — a detector that is accurate and fragile is still useful in settings where nobody is attacking it, and saying so is more useful than a number that quietly implies otherwise.

The current equilibrium, where the strongest claim is the least tested one, is not sustainable for a field whose entire premise is adversarial.

  1. The same has happened to essentially every static robustness benchmark in adversarial ML. It is a reason to plan for regeneration, not a reason to avoid building them. ↩
